# GPR + PSO Renewable Forecasting (Karnali Province, Nepal)

Coursework Task 1 implementation: Gaussian Process Regression (GPR), tuned by a
hand-written Particle Swarm Optimiser (PSO), forecasting solar irradiance and
wind speed 24 hours ahead from NASA POWER hourly weather data, with the output
thresholded into Low/Medium/High generation classes via Gaussian Process
Classification (GPC), benchmarked against Persistence, Ridge Regression and
SARIMAX baselines.

## Site

The final dataset (`data/raw/nasa_power_hourly.csv`, copied from
`karnali_center_hourly_2025.csv`) is centred on **29.267°N, 82.183°E** --
right by **Jumla**, Karnali Province, Nepal, matching the region the proposal
names by name. Two earlier candidate extracts (Kathmandu Valley at
27.71°N/85.32°E, and Surkhet at 28.6°N/81.6°E) were tried and discarded during
setup; `src/data_prep.py` can still read either of NASA POWER's two export
layouts (its native `-BEGIN HEADER-` format, or this flat
`Location,Latitude,Longitude,...` format) via auto-detection, so swapping the
source file again in future only needs `LATITUDE`/`LONGITUDE`/`ELEVATION_M`
updated in `src/config.py`.

## How the forecast is framed

Data is hourly for all of 2025 (~8760 rows, one NASA POWER grid point).
For each of the two targets (solar irradiance, wind speed):

- **Inputs** (52 features -- justified by ablation against the proposal's original 8):
  surface meteorology (temperature, humidity, wind speed, irradiance, cloud amount);
  cyclical seasonal (day-of-year sin/cos) and diurnal (hour-of-day sin/cos);
  analytically derived physics (solar zenith angle, air mass, wind speed cubed);
  lags at 1, 2, 3, 6, 12, 24 hours; and rolling 6h/24h windows. (A rolling-3h
  feature was diagnosed and dropped -- see `src/features.py` -- as an exact
  linear combination of lag1/2/3 that caused rank-deficiency in Linear Regression).
- **Target**: the same variable **24 hours later** (same hour, tomorrow) --
  this is the "day-ahead" framing the proposal's introduction motivates
  (diesel/battery planning needs tomorrow's number), just produced once per
  hour instead of once per day.
- **Solar is restricted to daylight hours** (rows where measured irradiance
  is already > 0). Night-time solar is trivially 0; scoring every model on
  it would inflate every RMSE/R2 identically and hide what actually matters.
  Wind uses all 24 hours.
- **Split**: chronological (never random -- shuffling would leak the future).
  Train = Jan-Aug 2025, Val = Sep 2025 (used only for PSO's fitness function),
  Test = Oct-Dec 2025 (final, held-out, reported numbers).
- **GPR-family models train on a random 700-row subsample** of the training
  window (exact GPR is O(n^3); PSO needs hundreds of refits). Persistence,
  Ridge and SARIMAX use the full training window since they scale linearly.
  This choice is explicitly aligned with the proposal's own framing --
  "GPR ... performs well on small, incomplete datasets."

## Models compared (per target)

1. **Persistence** -- naive "tomorrow same hour = today same hour".
2. **Ridge Regression** -- same 41 features, full training window.
3. **SARIMAX(2,0,2), no seasonal term** -- univariate time-series baseline,
   walk-forward state updates (`append(refit=False)`, forecast 24 steps
   ahead each time) so it only ever sees real past observations. A
   24h-seasonal term (`seasonal_order=(1,0,0,24)`) was tried first and made
   each of the ~5,800 walk-forward steps too expensive to finish in
   reasonable time; treat SARIMAX here as the "naive time-series-only"
   baseline -- the GPR/Ridge models already see the diurnal cycle through
   hour_sin/hour_cos and lag24.
4. **GPR, RBF kernel, sklearn's own optimiser** (L-BFGS-B, 5 restarts).
5. **GPR, Matern(nu=1.5) kernel, sklearn's own optimiser.**
6. **GPR, RBF kernel, PSO-tuned** -- the project's core contribution. PSO
   searches (length_scale, signal_variance, noise) to minimise validation
   RMSE, over the *same* bounds sklearn's optimiser searches, for a fair
   "PSO vs default-tuned" comparison as the proposal specifies.
7. **Gaussian Process Classification** on the same features, predicting
   Low/Medium/High (tertile thresholds computed on the train split only).

## Results snapshot (final run, Karnali/Jumla data, Oct-Dec 2025 test set)

| Target | Best model | Test RMSE | vs. persistence | vs. default GPR |
|---|---|---|---|---|
| Solar irradiance (kWh/m²/hr, daylight only) | **PSO-tuned GPR** | 0.0837 | -3.6% (persistence 0.0868) | -18.8% (default RBF-GPR 0.1031) |
| Wind speed (m/s) | Persistence (0.5625) beats every learned model | 0.5625 | -- | PSO-GPR (0.6341) is the best learned model, -0.9% vs default RBF-GPR (0.6398) |

Honest findings worth writing up in the Discussion section, not hiding:

1. **For solar, PSO-tuned GPR is the clear best model overall** -- it beats
   persistence, Ridge, SARIMAX, and both default-tuned GPR kernels. This is
   the headline result for the project's core claim.
2. **For wind, naive persistence is hard to beat.** Jumla sits in mountainous
   terrain where hour-to-hour wind is strongly autocorrelated but also
   locally chaotic (note SARIMAX's very poor $R^2=-4.06$, and Ridge actually
   *underperforming* persistence too) -- a genuine, reportable finding about
   terrain-driven wind variability, not an implementation bug. PSO-tuned GPR
   is still the best of the *learned* models, evidence its tuning helps even
   where it does not out-forecast the naive baseline.
3. PSO's chosen kernel hyperparameters are interior optima (not pinned to a
   search-box edge) for both targets on this dataset -- a cleaner result than
   the earlier Kathmandu/Surkhet trial runs, worth noting in the report as
   evidence the search space was well-chosen for this data.
4. GPR's predictive mean can dip slightly below zero at night for solar
   (visible in `solar_forecast_uncertainty.png`) since nothing constrains
   the Gaussian process to be non-negative; the Streamlit app clips this for
   display, but the underlying model is unchanged -- worth a one-line mention
   as a limitation/future refinement in the report.

## Running it

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
# On Windows:
.\.venv\Scripts\activate
# On Linux/macOS:
source .venv/bin/activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Run the full training and evaluation pipeline
python run.py                          # full pipeline: ~2-3 minutes

# 4. Launch the interactive Streamlit dashboard
streamlit run app/streamlit_app.py     # opens live dashboard at http://localhost:8501
```

In VS Code: select the `.venv` interpreter (`Ctrl+Shift+P` / `Cmd+Shift+P` -> "Python: Select Interpreter" -> `.venv`), then either run `run.py` directly or launch the Streamlit app.
